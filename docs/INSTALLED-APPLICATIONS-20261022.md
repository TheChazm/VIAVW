# Installed applications and direct Codex use — October 22, 2026

Codex directly operated the installed copies of Microsoft Word, VLC and 7-Zip through VIAVW, inspecting captured images/accessibility, choosing actions, and checking actual files. The applications were unmodified; generated ZIP/RTF/AVI files were disposable input data. This extends compatibility evidence beyond specially written applications and beyond launch-only checks. CharlieAI remains unchanged.

Word's DOCX was created by **Word's Save As dialog**, not generated by a document library. Inspection of its ZIP/XML verified both paragraph strings, a bold first paragraph and archive integrity. It was then reopened in a fresh Word instance, captured and checked through accessibility. A separate test moved from Ctrl+Home to the second line using a mouse click, then Home/Shift+End selected **the second paragraph**; the image and accessible selection confirmed that the pointer changed the caret location.

The two Word files had different saved markers; the second file's marker did not appear in the first. VLC's paused six-second image remained unchanged in the later observation, and its snapshot PNG was written inside the project. Two 7-Zip extraction runs produced the expected files. Three different application layers also coexisted in one host during direct use.

## Failures retained and lessons

Word's disappearing splash exposed a stale main-window assumption: observation threw `Sequence contains no matching element`. The research build now replaces a missing main HWND only when one visible, titled, unowned top-level window belongs to the same application PID. Multiple candidates stop automatic selection. Nine safety checks cover ambiguity, helper processes, hidden/untitled windows, popups and existing roots; actual Word startup demonstrated recovery.

An attempted keyboard route through Word's Save As format selector did not act on the intended control and saved an unintended **disposable** `☻.rtf`. That file and the observations remain. Explicit mouse targets from the owned control geometry selected DOCX and verified the complete intended filename before Save. The Office upgrade prompt ignored a forwarded native click; Enter accepted it. This is evidence against treating message delivery as completed UI action. Some format-dropdown text also showed repaint artifacts.

Initial cold-launch Word smoke runs passed window/handoff checks but failed the bounded graceful close, requiring explicit disposable-job cleanup. An experiment prioritizing a known close HWND did not solve it and was **reverted**; its separate build/source remain preserved. A title alone was too early a readiness criterion for this preset. The launcher now checks Word's actual accessible document text before handoff. Two consecutive Word repeats and the final public-suite run passed after that change. Additional untouched DOCX/RTF direct runs closed normally. These observations support content-readiness checking; they do not prove the precise cause or guarantee every Office close/save prompt.

Physical human acceptance of the new presets remains pending. API posted-click results do not establish that every existing viewer pointer adaptation behaves identically. 7-Zip's viewer still has the documented synchronous-click/menu limitations.

## Implementation and preservation

- Separate `Apps-20261022b` research executable with verified source/PDB snapshot; the accepted Visual Studio viewer and ordinary API executable selections remain unchanged.
- Conservative splash-window replacement, explicit owned `surface` selection, optional `captureMode:"print-window"`, and optional click `deliveryMode:"posted"`. Defaults remain window DC and synchronous clicks.
- `scripts/viavw-console.py`: persistent direct Codex control, historical response deduplication, bounded observation tokens, local response/timing evidence, shared ownership and graceful shutdown. [Direct-control instructions](CODEX-DIRECT-CONTROL.md) describe the protocol.
- Three installed-app viewer presets and repeatable console/surface/regression checks.
- The existing workspace helper now returns the **post-show** inspector state after requesting Human control; its former return value preceded showing the viewer. Its ownership/transport/workspace checks were rerun.

No driver, global hook, privileged Windows change, physical input injection, global Office graphics setting, or CharlieAI edit was used. Word was started with its documented [`/a` option](https://support.microsoft.com/en-us/office/lifecycle/command-line-switches-for-microsoft-office-products); VLC's documented [separate-instance behavior](https://docs.videolan.me/vlc-user/desktop/3.0/en/advanced/player/play_multiple_instances) informed its launch configuration. 7-Zip can retain normal per-user window/history settings; these tests are not a filesystem/settings sandbox.

## Verification, performance and cleanup

The research executable passed the existing **33** installed Notepad++/Visual Studio protocol checks in the initial run and a fresh repeat. The real 7-Zip console suite passed **13** checks, including exact extracted contents, duplicate submission without new input, conflicting IDs, stale plans, ownership and cleanup. Nine surface-selection safety checks passed. The adjusted workspace passed its 18 transport/policy tests, 19 installed-application checks and collaboration smoke. Requested experimental modes are rejected on older hosts rather than silently ignored. All three new preset smoke paths passed in the final public command; these do not substitute for physical human acceptance or replay every direct Word/VLC workflow.

**That public command still exited with a failure:** a deep VS accessibility request exceeded the existing 5000 ms worker limit, which terminated its owned layer to contain the stall. The failed report is retained at `artifacts/installed-apps-regression-ea3cfa77b02c46509e07e55acc5ae62f`. A fresh full 33-check repeat passed without changing code or timeouts, so a clean repeat alone did not resolve the fault. That historical build and the unchanged accepted API can end the application layer and lose its unsaved state. The later isolated-read experiment below addresses this failure mode in the research build. Deep accessibility remains opt-in; the limitation materially constrains unattended use.

Five Word capture/export requests without deep accessibility took **85.9 ms median**, range **74.8–148.1 ms**. Across the measured interval, eleven selected application/worker processes accumulated **0.125 CPU seconds** and summed to approximately **768 MiB of working sets**. The host/console were excluded, shared pages can be counted multiple times, and the interval included tool turnaround. These figures are not unique memory allocation, GPU measurements, per-keystroke latency or foreground equivalence. Deep accessibility is a separate cost.

Read-only desktop samples covered most direct experiments and a separate complete DOCX session. The first monitor began after the initial 7-Zip launch. Input-desktop and confinement geometry stayed stable; tested app/worker PIDs did not appear in foreground samples. Physical input occurred, so pointer/focus equality throughout those intervals is **not** claimed. The protocol regression has its own monitor and cleanup result.

All direct consoles and owned test applications were closed. Earlier cold-start failures were force-cleaned only within their disposable jobs. Final process/storage/preservation details and evidence paths are recorded in `artifacts/installed-apps-20261022-final-audit.json`. Earlier approximately 322 MB browser profiles were retained without deletion attempts.

## Follow-up: remove inspection from the interaction wait

Research build **Apps-20261022l** retains the private desktop and existing serialized input worker, but moves passive tree/menu scans to a separate, reusable helper job. `inspect-begin`/`inspect-poll` return without waiting for providers. The helper streams partial snapshots and has a 750 ms provider deadline, with a separate background 1500 ms cold connection limit. A stalled read stops its helper rather than disposing the application job. Input, ownership and surface changes explicitly invalidate the context of asynchronous evidence. Compatibility reads wait at most 100 ms per query and withhold old nodes after input/ownership changes. See the direct-control instructions for the protocol and remaining limitations.

An installed 7-Zip experiment deliberately hung the read helper, opened/cancelled the actual Copy dialog in both independent sessions, observed the timeout and then successfully inspected/interacted again. Both application PIDs survived. Healthy scans reused the same helper. These checks establish fault separation for this passive read path; they do not prove that all UIA providers, pointer adaptations, capture operations or applications are fault-safe.

The first new prototype exposed a compatibility scheduling error (a pending general scan blocked the requested editor scan); it was corrected to return incomplete/busy evidence rather than fail an observation. An initial test also targeted the wrong 7-Zip class, and another lacked the ordinary list click/focus preparation; those failed test reports were retained. A subsequent full run passed editing but failed the old strict two-second VS exit assertion. The verifier now observes status for up to three additional seconds without resending close or dismissing a prompt, and still fails if the IDE does not actually exit. This change concerns shutdown observation, not interaction delay. Earlier timeout and failed runs remain under artifacts.

Final follow-up verification and measured timings are recorded in `artifacts/installed-apps-20261022-final-audit.json`. Accepted normal viewer/API executable selections remain unchanged; installed-app presets and the direct console select the hash-checked research build.
