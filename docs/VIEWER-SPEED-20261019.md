# Viewer speed investigation — 19 October 2026

The normal demonstration now uses reusable private-window DC capture for the installed Visual Studio 2022 software-rendering profile. It preserves the multithreaded viewer, serialized input, explicit Human/Automation ownership, state-preserving handoff, bounded capture deadlines and owned-process cleanup. The previous verified printing build remains available through `-PrintCapture`. Foreground-equivalent speed and physical human acceptance remain unverified.

The capture thread retains a memory DC and a top-down DIB backed directly by its reusable pixel mapping. It acquires/releases the source window DC for each frame, flushes GDI writes before signalling completion, and recreates destination resources on resize or mapping growth. Readers receive immutable copies and interpret this opaque source as RGB; existing ARGB transport retains transparency. Owned popups retain their printing path and are drawn into the destination. Synchronous inspection now uses the selected DC root backend too, so a hidden PrintWindow root refresh cannot mask a DC failure.

This follows the documented [mapping support in CreateDIBSection](https://learn.microsoft.com/en-us/windows/win32/api/wingdi/nf-wingdi-createdibsection), [GdiFlush synchronization](https://learn.microsoft.com/en-us/windows/win32/api/wingdi/nf-wingdi-gdiflush) and [memory-DC thread ownership](https://learn.microsoft.com/en-us/windows/win32/api/wingdi/nf-wingdi-createcompatibledc). It introduces no driver or system-wide interception.

Two alternating seven-burst runs per backend, using the corrected measurement driver:

| Earlier DC copy | 93.2 ms / 77.4–139.7 ms | 12.5 ms / 10.6–16.4 ms |

The capture saving is measurable. Total glyph feedback remains variable and does not establish a large responsiveness gain. The probe detects new source glyph pixels partway into a 20-character burst; actual complete editor text and the saved file are checked separately. It measures neither physical scanout nor every character's visual latency. The same-driver click/Enter/typing report medians were 62.1 ms with the preserved L printing viewer and 46.4 ms with AA; Backspace/immediate-typing medians were 58.4 and 45.1 ms. These report acknowledgements can precede fresh glyphs.

The longer activity test submitted 200 separate characters at 50 ms intervals. All characters reached the actual IDE in order and the exact final file saved. Over 10.0 seconds, the tracked process tree used 12.0 CPU-seconds, about 120.3% of one logical core, and the observer sampled 231 frame publications. This includes Visual Studio and its helpers, excludes the later explicit text/image verification, and is not whole-machine utilization or per-character display latency. It has no paired sustained-CPU baseline. The short editing sample's summed per-process peak working sets were 2.9 GiB; those are not unique or simultaneous RAM. Human idle produced 4 frames over about two seconds and 93.8 ms viewer CPU; Automation idle produced 0 frames and 0.0 ms viewer CPU after the watches expired. Idle figures exclude source/helper CPU. The earlier 22% workstation observation remains unexplained.

Three findings changed the work:

- The first mapped-DC candidate passed state checks but produced solid magenta menu rectangles. It was rejected and its owned test job closed. Reading an ARGB bitmap's temporary drawing DC was the faulty popup-copy path. Drawing the bitmap into the retained destination fixed it. New popup/clipping tests and a VS-specific screenshot check catch that failure; the check was verified against the actual saved bad image. Representative corrected menus, designer and editor images were inspected. This is a targeted visual guard, not a universal image-correctness oracle.
- A mouse run left the inserted marker visible but unsaved. Its driver still used a fixed 250 ms pause before Save. It now waits for complete forwarding and actual editor text before the dependent shortcut; the fresh full mouse/editing run passed.
- Initial profiling showed 1.2–1.4-second waits after Inspect details. The driver re-clicked Inspect on automatic frame changes, queuing extra UIA work before measured input. With one explicit inspection outstanding, the unchanged AA viewer's Backspace report median was 45.1 ms. Original samples remain in the [AA index](../artifacts/vs-speed-20261019-aa-evidence.json); use the [AB timing follow-up](../artifacts/vs-speed-20261019-ab-timing-evidence.json) for performance conclusions. Explicit accessibility inspection itself remains slower than ordinary refresh.

Final AA verification passed 29 workflows, 66 bounded nested menu paths, 15 mouse checks, 32 editing checks, 25 mapped-DC checks, 13 capture/lifecycle checks, 25 existing transport checks and three actual worker/helper restart races. The corrected performance driver repeated all 32 editing checks on AA and the previous printing viewer. Real workflows include opening/switching/editing/saving files, selecting/deleting/undoing actual text, scrolling, menus/dialogs, building, running a child application, breakpoint/step/continue/stop, error correction, designer/code switching, project generation and ownership handoff. The menu sweep opens submenus up to depth three; it does not execute every leaf command or cover every workload/extension. Small fixtures are confined to deterministic pixel/lifetime/hang tests.

The destination adds two GDI objects: its test process measured 4 before, 6 during and 4 after. Repeated resizing, 200 fresh frames and 30 independent popup-surface lifetimes released their objects/maps. A stalled-print test still verified bounded containment of only its owned layer while another layer remained usable. Its fast posted-input RPC is not evidence that the deliberately hung application processed input. A short GPU-counter sample during an earlier menu run showed small allocations and no sampled engine activity for the software-rendered IDE; it does not establish zero wrapper GPU cost. Native GPU-rendered VS capture remains unresolved.
